# Native performance worker — independent source review

October 20, 2026. **Source review and the bounded synthetic-command native output lifecycle are accepted after gate5 and proof3.** The final workspace gate passed 709 cases, including 16 session tests; formatting, warning-denied Clippy and default all-target build passed. Proof3 exercised actual output, normal Finish, real retirement, exact retry, Stop retention and archive restoration. The earlier failures remain documented below. This reviewer inspected source and artifacts, opened no device, ran no Cargo command and edited no production code. Musician-facing recording UI and the broader release remain unqualified.

## Reviewed implementation

The new `performance_session.rs` integrates the existing production live renderer/tap and incremental writer under three owners. The IPC-side session admits commands and returns bounded snapshots; a concrete native thread creates/plays/pauses/drops the CPAL output stream; a separate drainer owns the tap receiver and writer. There is no input-stream call in this path. The original remains logical post-mix F32, independently of native F32/I16/U16 conversion.

Start returns its stable attempted identity before device/SQL preparation. Exclusive stage creation prevents an existing directory from being resumed. The journal/drainer precede native play and Ready. Same-process retries bind the complete Start request; the existing-stage rule is inspect-only after worker replacement. No descriptor hash means creation is unconfirmed, not absent. The exact device/format is live status rather than an undocumented alteration of the v2 original descriptor.

The native constructor of `NativeSealPermit` is private to the concrete I/O module. Its path requires a real played stream, observed callback Finish, successful pause/drop, actual outer renderer/error destruction and tap-producer destruction. The permit retains the controls and exact identity/cut; public status booleans cannot construct it. The drainer additionally waits for producer destruction and empty queue. `PerformanceWriter::seal_native` checks the healthy terminal context, complete/durable Finish counters, absence of partial/pending writes or capture faults, semantic checkpoint review and exact full `CompletePrefix` before authorization/final transaction. Same-attempt seal retries retain their operation and full original receipt.

Session snapshots use `try_lock`; session Drop cancels/detaches rather than joining or doing SQL/native I/O. Absolute phase deadlines are independent of parent traffic. A blocked call is not claimed cancelled: the retirement latch prevents new generation admission. The whole admission lease is retained on unproven teardown, including failed/abandoned Ready handoffs. These are source properties; platform destructor behavior still needs actual qualification.

## Findings and corrections observed

1. **Inner renderer destruction was too early for the new handoff.** The existing inner `render_done` flag precedes automatic destruction of remaining renderer fields. The new concrete `RenderState` takes and fully drops the renderer before publishing its outer acknowledgment; `ErrorState` does the same for the real error guard. `Controls::destroyed` requires both outer flags plus inner/tap evidence. Admission retention and native proof use that combined check. The owner added software tests exercising the actual wrapper destructors; those tests do not represent native stream retirement.
2. **Scoped faults could race normal-seal authorization in the wrong order.** The first session version published `LiveControl` fault before competing with the writer's authorization CAS. A writer could observe a healthy cut, then authorize after that fault but before cancellation reached the gate. `PerformanceSession::fault` now first competes `ACTIVE → CANCELLED`, then publishes the requested cause and tap cancellation. A late fault after `SEAL_AUTHORIZED` rejects without mutating the frozen controls. This matches Stop's linearization and preserves the requested first cause. The owner regression for both branches passed in the central gate.
3. **Final storage writes needed a second mode check.** The CompletePrefix preflight did not by itself prevent triggers from introducing derived recovery rows or reversing state during final publication. The coordinator added postwrite complete-snapshot/state/verified-manifest equality before commit. The independent [storage review](RUST-COMPLETE-PREFIX-REVIEW.md) and its eight tests cover this, plus the cached-descriptor issue in borrowed inspection.

The shared status/parent code now cross-checks Finish scope and accepted fence, binds stage/take/path/readiness to the retained Start, preserves immutable descriptor/Ready/first error/cut/manifest fields, and rejects progress regression. Parent Finish drains the finite prior live queue before registering the expected worker-accepted fence. Stop remains a distinct cumulative ticket acknowledgment after actual session quiescence; a pending Performance status is not treated as Stop completion.

## Limits and remaining evidence

The first actual run exposed the Ready publication defect described below. Its correction and the deadline races were subsequently reviewed and gated; final proof3 acceptance is restricted to the exact short native scenario below.

- A native Finish cut, closure retirement, complete drainer state, seal authorization and committed manifest remain five different facts. An error after authorization is potentially committed; Stop cannot retroactively promise an unsealed original.
- Parent-local batches discarded by urgent Stop/Panic were never worker-accepted or callback-recorded. The current source has no persisted/public unforwarded count. Do not call all GUI-enqueued presses retained originals. Healthy Finish preserves the preceding finite queue instead.
- Full semantic/original verification performs bounded-memory but potentially substantial I/O. The configured phase deadlines are initial limits, not thirty-minute recording/sealing performance evidence. Long-recording usability must be measured separately.
- Fake/native-adapter tests may hold callbacks, force stalls and test the state machine, but must not manufacture a normal native permit or qualify CPAL teardown. Test the actual paired worker and same-built output path after the integrated source gate.
- Proof3 verifies Ready identity, original events/PCM, normal Finish/retry, Stop interruption, callback/error retirement and direct store publication/history/archive restoration. Musician-facing recording UI, performance-aware discovery/recovery, explicit attachment and durable pending-intent flow remain pending. The generic capture scan still rejects these 32-hex performance directories, and generic recovery correctly refuses owned performance journals. Listening, latency, sustained recording, MIDI2/MPE, plugins/models, Windows and the completed song remain open.

The actual `proof1` qualifier then failed after 1.25 seconds with `Recorded-performance status revision regressed or changed`. Its retained `.runtime/rust-performance-worker/proof1-run.log` is 844 bytes, SHA-256 `dcefafc401036df37af4ede38ccab8b19542b8accbdae809ab14a6696afd4dec`. This reviewer did not run the qualifier. A bounded read-only inspection of its isolated `proof1/store/captures/ba212fa8dbc14d39abf840cdc75188c3/take.sqlite3` found:

- 45,056 bytes, SHA-256 `dc7b64a67d7e1ffce8f8c29d44f6ff210eb6e4aa4cbb5c8107cdbec3ba5daa6e`, unchanged before/after this inspection;
- Recording state and v2 ownership, six initial stream-prefix rows;
- **zero committed chunks, zero sealed manifests and zero recovery metadata rows**.

The attempted stage is retained, but this failed run establishes no durable audio/event prefix, normal Finish, recovery result, archive closure or native UI acceptance.

**Runtime finding:** `receive_ready` changed `cached` identity/Ready/live/phase before `snapshot` compared its candidate to that cache. It can also run from `admit`/`begin_finish`, outside snapshot. Therefore a changed externally visible payload could reuse its prior revision. The corrected source stores immutable handoff evidence separately and leaves the last-published cache unchanged until candidate comparison/commit. Shared preparation cannot expose Ready before the actual admission lease arrives. Merely copying the cache after calling `receive_ready` would not fix this.

The independent follow-up also identified a held-lock fallback requirement: the immutable handoff must include the actual native sample-format evidence, or Ready must remain withheld until that evidence is present. Otherwise the first cached Starting snapshot plus a queued Ready can produce Recording/Ready with `native_sample_format: None`, which the parent correctly rejects. The corrected handoff includes the format; three new deterministic owner cases cover delayed handoff, previously published revision, and handoff via admission/Finish while the shared lock is held. This is source review; gate4/new-path native retry remain pending at this addendum, and the earlier source table remains historical.

The coordinator additionally identified that startup's deadline was cleared before the Ready handoff was queued. This could leave a preempted owner in Starting indefinitely while heartbeats continued, and an unconditional clear could erase a concurrent Stop deadline. The corrected source retains START through successful enqueue and uses a packed atomic phase/deadline word; compare-and-exchange clears only the observed START word. Expiration likewise claims its exact observed word. The new owner test interleaves Stop between observing START and clearing it, retaining Stop's exact deadline; repeated Stop cannot extend that deadline.

**Additional source finding, subsequently corrected:** `Shared::watch` initially preserved a same-phase deadline but replaced any different phase. `begin_finish` could publish its fence, be preempted before installing FINISHING, and resume after a concurrent fault installed STOPPING. Its 15-second Finish watch would overwrite the 3-second native-retirement watch. A fast completed callback could similarly reach DRAINING/SEALING before the delayed Finish watch. The final correction rejects same/earlier phase installation on every CAS attempt, while allowing the intentional Stop-to-drain transition after actual native retirement. The new deterministic owner test covers Stop, Drain and Seal deadlines against stale Finish and repeated calls.
