# Independent retained-capture recovery review

October 20, 2026. This lane reviews the bounded workflow in [NATIVE-CAPTURE-RECOVERY.md](../contracts/NATIVE-CAPTURE-RECOVERY.md). It owns independent recording/store tests and this report only. No production source, dependency, Cargo invocation, device, OS permission or native UI action belongs to this lane.

## Review requirements

Discovery and inspection must not imply capture completion. A read-only inspection holds the existing exclusive writer guard and one SQLite snapshot, refuses a live writer, and leaves the original DB bytes, recording state, interruption records, chunks and manifests unchanged. Scan must not create the captures directory or recursively search. Invalid stage names, redirected paths, multiple hard links and bounded-scan exhaustion need explicit diagnostics rather than actionable entries.

The reviewed inspection identity must bind the complete physical rollback-journal file, including corrupt and unselected tails. The verified-prefix index alone cannot do this: a changed bad payload can produce the same selected prefix, counts and error message. The backend owner adopted a streamed whole-file SHA under the read snapshot and ownership guard. Recovery must compare that reviewed identity before mutation and keep ownership continuously when transitioning to the writer. After interruption metadata changes intentionally, it must compare a separately normalized source/prefix proof rather than expect the old physical file hash to remain unchanged.

Source frame positions are not counts of successful PCM. A descriptor may start at frame 100, with two content frames and one known gap: its selected source interval is 100..103, its recorded count is two, and its gap count is one. A playable reference must use the selected source interval and preserve known gaps/unknown-tail disclosure. It must not synthesize frames 0..100, extend into a corrupt tail, interpret raw events as audio, or treat a gap-only stream as recorded audio. Recovered prefix attachment retains its original unknown tail; placing it at arrangement frame zero does not calibrate original capture time.

Recovery admission binds the caller's stable operation identity to the exact reviewed stage and inspection. An authenticated same-request retry may return its existing recovered manifest, including after a lost reply. A changed review, different operation or unrelated normal seal must not be accepted as that receipt. Recovery and project publication remain distinct commits. Attachment conflict preserves the recovered original; source closure through project history and archives includes the interruption proof and retained bad rows.

## Source findings and adopted resolution

Reading the initial implementation identified two preservation requirements before acceptance. First, pre-recovery whole-file SHA cannot by itself authenticate a retry after sealing legitimately changes DB pages. The selected manifest covers only the proven prefix, so changing an excluded bad row could otherwise leave the same selected receipt. `original_rows_sha256` now streams a type-tagged digest of the full original descriptor/chunk rows, cached stream prefix, SQLite sequence and stable schema, including unselected/corrupt rows. Derived interruption, recovery-index and manifest rows are authenticated separately; only intentional state/receipt additions are excluded from the original-row digest. Store replay checks this normalized proof and the exact selected audio/prefix against the original inspection.

Second, a caller could otherwise retain an old `inspection_sha256` while substituting a new original-row proof or audio summary. The store now recomputes the canonical expected DTO fingerprint from every field except the fingerprint itself before deriving the seal operation or accepting a replay. Independent cases exercise both altered original-row proof and altered recorded-frame count under the old token.

The reader owns a read-only/query-only SQLite transaction and existing ordinary ownership sidecar. It rejects symlink/hardlink journals and WAL/shared-memory ambiguity before database inspection. Transition to `Journal::open_owned` retains the same owner, acquires an immediate write transaction, and rechecks the complete reviewed inspection before recording interruption metadata. It then compares the normalized verified prefix before `seal_recovered`. Store action paths validate their canonical UUID-owned stage namespace again. No recovery starts a device, resumes the journal or automatically ingests/attaches it.

The initial schema enumeration read an unexpected `sqlite_schema.name` into an unbounded String before validating the fixed table set. It now checks SQLite type and byte length and selects a bounded substring before materialization. The final source digest enumerates all original columns, including extension columns, with a 128-column/256-byte-name bound, quotes identifiers, and rejects columns that shadow SQLite row identity. Table and column identities are part of the digest; only the controlled take state is excluded. Later SQL/text/blob hashing uses 64-KiB fragments. Acquisition and final seal each recheck the normalized original-row digest before their transaction commits, including after state/receipt writes, so a trigger that changes original rows rolls back rather than committing the change. Scan consumes at most 128 directory entries; reaching exactly that threshold conservatively reports that additional entries may remain. No concrete backend source blocker remains from this audit; the final central regressions pass.

## Attachment conflict workflow

The initial UI review found a workflow blocker, with the original still preserved. `RecoveryUi::blocks_session` locks the session whenever an attachment retry exists; every failed attachment retains that retry. Both request and dispatch then reject Refresh/Open. If the expected revision conflicts with a newer saved revision, retrying the unchanged request cannot succeed and the user cannot open that newer revision without restarting. The service currently marks all mutating errors as uncertain outcomes, including a store revision conflict, so the UI cannot infer a known rejection from the existing error fields or message text.

The adopted correction adds a typed `RevisionConflict` service outcome and an explicit, nonmutating keep-local decision once no attachment request is active. The typed conflict occurs before project/history/operation publication; `attach_capture` may already have durably ingested the original, so it is correctly described as unpublished rather than having written nothing. Read-only review of the correction confirms that the UI retains the sealed source and complete exact request/evidence in a suspended card, releases session navigation, and states that this does not cancel or undo a possibly completed attachment. Refresh/Open and explicit retry can then reconcile an uncertain result. Fresh choices remain disabled for that uncertain request. Only a typed known rejection enables explicit release, retaining bounded evidence of the old request before a new choice with a fresh operation ID and current saved revision. No expected revision is silently rebased.

The added headless source fixtures exercise inactive-only keep-local, evidence retention across scans, uncertain-versus-typed conflict classification, Refresh/Open/Save after release, reconnect without automatic retry, exact stale-request replay, and an explicit fresh attachment choice. These cases pass in the final central gate. No concrete workflow blocker remains in the reviewed correction. No app source was edited by this review lane.
