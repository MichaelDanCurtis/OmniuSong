# Exact ordinary archive SQL postimages

This stage applies to actual ordinary OSAR export, identity restore and restore-as-copy. It strengthens the existing completion and SQL-origin contract without changing catalog, archive or musical schemas. Nonempty performance-projection guards stay closed. It provides no new playback, source-adoption or AI authority.

It selectively supersedes the preceding outcome contract's identity-restore no-extra-hash description and its export cleanup inventory: identity now acquires/hashes a private input, and export also cleans its known digest spool file. Completion, uncertainty, origin and rollback semantics continue to apply.

## Independent plans

Identity restore first acquires a private no-overwrite archive snapshot and hashes the bytes it actually acquired. Validation and installation read that snapshot, never reopen the caller's mutable pathname. Context and retained restore diagnostics name the observed hash separately from the original pathname. This is an acquired-byte identity, not a caller-specified expected pin or proof that a concurrently changing source was a single coherent version; existing SQLite, checksums and closure validation must still pass.

Both restores hold their actual live writer transaction while capturing the complete persistent catalog baseline. Before the first live SQL mutation or final-path object placement, a disposable, trigger-free catalog-shaped database contains all independently planned project, history, operation, import, asset, take registration and copy-lineage rows. Its fixed DDL is application-owned. It never executes input schema SQL. Copy identities and operation mappings are allocated in this plan; the pending map is private, not a live-catalog temporary authority. The complete return value is also prepared before commit.

The expected postimage is the full baseline plus that planned additive overlay. Existing keys may be reused exactly once only for assets, native take registrations, copy proofs and proof-operation mappings. A reused row must match every cell; project/history/operation/import/admission collisions and duplicate planned keys refuse. A one-shot freeze prevents late plan updates from changing the expected digest. The actual applied rows may be read from the private plan, but a coherent later rewrite of that plan still fails comparison with the previously frozen expectation.

Export uses an empty expected set and its fixed fresh output schema. Project, history, operation, import, asset, take registration, chunk and archive-meta expectations come from the fixed live source snapshot, format constants or original source buffer before their corresponding private output insertions. The existing bounded lineage copier validates and writes private lineage rows first; their expectations then come independently from the same held source snapshot before freeze. Expected values never come from the written output. Every listed cell participates before output commit/link publication. After that exact comparison, strict fixed-format OSAR schema validation independently rejects any additional trigger or index, including harmless additions captured before row planning.

## Exact comparison

The ledger covers all thirteen current persistent catalog tables, including recording intents and performance review/action rows unrelated to the restored project. It fingerprints the persistent schema, including trigger/index SQL, application ID and schema version. Unsupported persistent tables, views, virtual/WITHOUT ROWID tables, generated/extra/missing columns, altered declared types, defaults or primary-key layouts refuse rather than being omitted. The same baseline schema must remain at final verification. Application-owned archive-v1/v2 layouts are separately defined; v1 reads remain compatible.

Each row proof frames table identity, ordered columns, exact SQLite storage classes and bytes. NULL, INTEGER, REAL, TEXT and BLOB differ. Integer bytes and raw floating-point bits are retained; text is hashed as bytes, including embedded NUL. Typed composite primary keys use bounded unambiguous encoding. Final scans use physical `NOT INDEXED` rowid traversal into a separate observed key/hash index. Sorted per-table digests include exact key sets and row counts. A missing/extra row, valid same-count replacement, storage-class change, unrelated row swap or unplanned local row refuses the transaction before commit. Schema-only, row-count-only and semantic project validation cannot substitute for this comparison.

The digest proves SQL rows under these layouts, not complete physical database bytes or external object identity. The existing object/closure checks remain required. Final installed-path authentication under a governed held-source context is still separate work.

## Admission and resource limits

These ordinary routes intentionally retain their legacy transaction constructors and pass no inspection governor. They do not gain cumulative SQL-VM cancellation, a cumulative work budget or a hard time bound. The reusable ledger accepts an optional borrowed existing governor; it never creates a replacement budget, and owns a progress hook only on its disposable spool. A source/destination handle's progress ownership remains its caller's responsibility. Helper governor tests do not qualify actual ordinary archive governance.

This stage adds explicit safe-refusal ceilings: each full-value private catalog plan has a 512 MiB main-file limit; each digest spool's expected and observed indices together have a separate 512 MiB main-file limit. SQLite journals, temporary files, filesystem overhead and retained failed staging are outside those main-file limits. Total source observations and ledger row insertions share a 4,194,304 counter, so a row can consume multiple credits. Keys have a 256-byte encoded ceiling, layouts at most sixteen columns, and the persistent schema at most 256 objects with 64 KiB SQL definitions. Existing per-field ceilings remain compiled into each layout. Raw-byte accounting uses checked arithmetic; it does not itself impose a new cumulative-byte allowance.

Large field hashing requests at most 64 KiB per Rust substring buffer after type/length checks. With a governor, each separate substring/CAST query prepays full-cell interpretation again as well as its returned buffer, because SQLite may rematerialize the cell. This does not promise a bound on every SQLite internal allocation, filesystem stall or schema/transaction control operation. The full-value plan stores metadata and legacy assets, not full native take file payloads. A previously accepted catalog exceeding a new layout/field/plan/ledger ceiling now safely refuses these operations with retained diagnostics; no existing rows are deleted to make it fit.

Disposable plans use journaling disabled and are never reopened or adopted as authority after failure. Frozen expectations are one-shot in-process values, not durable recovery receipts. Failed work retains its staging; no automatic retry/adoption is added. Export success removes its known archive and digest spool files, then removes only its empty stage. Cleanup errors after durable output or committed catalog remain successful outcomes with warnings under the preceding contract.

Independent typed-cell framing and full-key-set tests supplement those real-route cases. Real lowered spool `SQLITE_FULL` and malformed private SQLite must retain private SQL origins. Fingerprint the original regular studio and installed app before/after tests using the coordinator only.

This backend stage creates no native control or application bundle. Native success-warning transport, one governed held context, final installed-path checks, coherent projection export/both restore activation, guarded readers/attachments, durable admission, exact-binary native walkthrough, physical hardware/listening and Windows acceptance remain separate.
