# Performance project consumers

This stage connects structurally valid schema-3 performance projects to library metadata, explicit read-only loading, selected waveforms and both recording-publication consumers. It preserves the existing source-aware load/edit/history and governed archive contracts. No catalog, musical or archive version changes. It supplies no native performance-conversion control or durable native archive admission.

## Metadata and actual sources

`NativeStore::list_with_budget` and `check_project_metadata_admission_with_budget` own a short catalog transaction under the supplied governor; their existing convenience methods supply the default limits. The shared metadata helper requires a caller-held transaction, reads bounded identities and raw lengths first, prepays decoding before a separate capped payload read, then validates document structure and exact ID/revision. It never opens a recording or registration. Valid nonempty schema 3 is permitted only on these explicit metadata paths; the legacy guarded decoder remains closed.

`ProjectSummary.source_authentication_required` is true for a structurally valid nonempty projection registry. False never proves source integrity. A valid metadata row retains its name/counts and no structural problem; malformed envelopes retain damaged-summary behavior. SQL/governor failures stop the list and are not disguised as a damaged song. Collection refuses the 513th row before payload decoding, with a paging-required error; no project is deleted or silently omitted. Library paging beyond 512 remains required. The native row notice says original performances are checked when opened; that source change is not a qualified installed-window workflow.

`NativeReader::load_document_with_budget(&mut self, id, budget)` is a standalone read. It owns a deferred catalog scope, authenticates held registered originals for the current document, verifies assets, projection semantics/geometry, registrations and owned paths, then rolls back the read transaction. It exposes no writer/migration/recovery capability. Its SQL concerns this same studio catalog; callers must not relabel that failure as an unrelated private/input database. This does not give it authority to retire a separate writer handle.

The reader's catalog descriptor is owned by SQLite from open through close, including all refusal paths. A separate raw OS open/read/close can release another same-process connection's POSIX locks; the original implementation's header peek reproduced that defect with an actual external writer probe. The corrected eventual read-only/no-follow connection supplies a borrowed `FILE_POINTER` for fixed 20-byte `xRead`, `xFileSize`, and `HAS_MOVED` checks before schema SQL and again afterward. The pointer never escapes and is never closed or freed by application code. Path metadata remains an additional nonsymlink/single-link/identity/length fence. Genuine SQLite return codes retain their database domain. A VFS without file-identity support refuses; Windows reader identity support remains an implementation/platform gate. No immutable/nolock connection or raw-FD fallback is admitted. The pinned build must retain the actual WAL-header/no-new-shared-memory and malformed/short-header refusal regressions; this does not promise safety under hostile concurrent journal-mode or path changes after the final fence. See SQLite's [raw-close locking hazard](https://www.sqlite.org/howtocorrupt.html#_posix_advisory_locks_canceled_by_a_separate_thread_doing_close_), [file-control contract](https://www.sqlite.org/c3ref/file_control.html), and [I/O methods](https://www.sqlite.org/c3ref/io_methods.html).

The old guarded `NativeReader::load_document` and short `read_snapshot` retain their contracts. The explicit `load_document_metadata_with_budget(&self, id, budget)` is available only inside a held snapshot and supplies structural metadata, not projection proof. The existing snapshot retains its legacy SQL-control limits; this is bounded payload prepayment, not a new whole-snapshot VM guarantee.

Selected waveform preparation uses that explicit metadata view, then independently authenticates only the requested media and retains its existing size/sample/channel and cancellation limits. Coherent false note claims elsewhere can remain readable metadata while the selected original's peaks are valid; active song loading still rejects those claims. The metadata budget captures cancellation at construction; existing callback fences bracket the snapshot and later selected-source work. No new whole-operation cancellation latency or deadline is promised.

## Recording publication

`publish_take_with_budget` provides the source-aware atomic project mutation; `publish_take` supplies the default governor. Exact recorded metadata receipt lookup precedes caller cancellation and the fresh projection-operation namespace restriction, under a separate finite metadata governor. The request, stored ID/lengths, hashes, historical identity/revision and exact requested track/clip are checked before returning a recorded receipt. It opens no original and never reinstalls an old document. A recorded receipt is a historical fact, not current usability or source authority.

Fresh publication uses the caller's single cumulative governor. It verifies current revision and exact immutable registry equality, collects current and candidate source references together, then holds one union source owner and its authentication through commitment. Incoming ordinary audio remains ordinary; performance-role originals receive actual performance authentication. Current bindings are rederived; after registry equality, the candidate needs geometry/source-window checks rather than another interpretation of the same binding. Assets, exact registrations and owned-path identity are rechecked at the final fence.

`publish_source_attachment` uses the same project mutation with the existing dedicated operation namespace and complete source-action history fence. Its caller still supplies the actual typed Prepared/Verified choice and held copied-source view. The bridge repeats whole-history checks, plans the opaque action row from the exact pre-mutation review/payload/history using a fixed trigger-free private catalog, then commits that row with the project/edit/operation. Opaque history never becomes source authentication. Every full history materialization is prepaid, including private population and append pre/post passes and live append pre/post passes. Larger valid histories can safely hit existing limits.

Normal `attach_capture` first uses bounded structural admission and source-independent historical receipt lookup. New capture ingestion deliberately retains its existing authorized legacy export path; a bounded read-only SealedJournal is still forbidden to export. After ingestion, project publication uses the new governed source-aware method. Normal ingestion itself is not newly qualified as one-budget/VM-governed. An imported owned original may remain after a later project conflict or refusal. Dedicated recovered-copy ingestion retains its separately qualified held-view path.

The ordinary SessionService AttachCapture response still loads current state on replay and prepares the library after commitment; that legacy generic reply can report a later failure without transporting a separate compact commitment. This stage does not claim the newer archive or recovered-attachment result semantics for it. Dedicated recovered attachment already separates committed history from optional current document/error. Typed normal publication completion remains required before broader native promises.

## Independent SQL plan and errors

Before any project mutation, a bounded postimage ledger captures all thirteen catalog tables and schema. Exact preimage CAS replacement/removal overlays the planned project row and pruned future history, then adds the new edit/operation and any planned source-action/review rows. Replacements require the same primary key and untouched baseline digest; mismatches poison the plan. Remove then insert at one known key supports replacing a pruned edit edge. Expected values never come from the applied destination.

The project-row CAS uses exact prepaid stored payload bytes, preserving valid noncanonical JSON. New history/result encoding remains the application's canonical serialization. The ledger freezes before live writes and compares every table/schema afterward, so a valid same-count unrelated-row substitution refuses and rolls back. Final source/asset/registration checks remain necessary alongside SQL equality.

The complete ledger also independently freezes every new operation column, including request/result bytes and hashes. A fresh receipt is built from the saved document only after it equals the planned document; it does not decode the newly written full result again. The complete exact SQL comparison still verifies that actual operation row. Historical lookup retains its separate exact metadata checks. Actual coherent valid-result-plus-matching-hash substitution and successfully ignored operation insertion must both refuse, roll back every table/schema, preserve all original bytes, and permit a clean exact retry after the trigger is removed.

Repeated full-cell `substr(CAST(... AS BLOB))` queries caused a real cumulative-work regression for the existing 2,000,000-byte native metadata fixture. The ledger now gathers bounded type/length headers first, then prepays a conservative whole-row traversal allowance before each actual value read, including a tiny scalar following a large field. TEXT/BLOB bytes use SQLite-owned read-only incremental handles, exact preflight lengths, a buffer no larger than 64 KiB and sequential `read_at_exact` calls. The per-handle/scalar allowance is twice the bounded row bytes plus 8,192, with separate buffer and per-chunk work credits; limits and the fixture remain unchanged. Storage-class tags and raw byte framing retain their previous meaning, including database text encodings. This is a logical-work model, not a pager-memory, physical-I/O or latency bound. Direct incremental reads do not run the SQL progress hook; cancellation is checked between chunks. A blocked single pager read is not interruptible by this contract. No raw descriptor, write or expired-handle retry is introduced. See SQLite's [incremental open](https://www.sqlite.org/c3ref/blob_open.html), [read](https://www.sqlite.org/c3ref/blob_read.html) and [close](https://www.sqlite.org/c3ref/blob_close.html) contracts. The existing pinned rusqlite version gains its `blob` feature; no package/version dependency change is required.

Every opened incremental handle is explicitly closed before its caller can roll back or commit. A close-only error retains its actual SQLite cause and a cleanup marker; a dual failure retains both primary and close causes. Only an actual live-catalog origin may supply catalog retirement, with fatal-code priority and conservative retirement on failed live cleanup. Input/private cleanup never gains that authority. Both disposable own-interrupt finalizers preserve failures carrying cleanup, and catalog abort retains unusable-connection information. Known-success cancellation checks occur after successful close; a later stop cannot erase a read or close error. Constructed secondary-error controls qualify this bookkeeping, not a physical disk or close failure.

The private planner and postimage spool retain their existing 512 MiB main-file caps and caller budget. Journals, temporary allocations, fixed controls and filesystem stalls are outside that promise. A disposable SQL scope maps only its tracked own INTERRUPT to the sticky cancellation/quota cause. Physical/semantic errors retain their domain; an input/private error cannot retire the live catalog. Shared lower recording finalizers retain their previously documented error-priority limits.

Private scratch retains failed diagnostics. On a completed commit, best-effort cleanup touches only remembered file identities and an empty directory, never recursively following or deleting new members. The planned file's identity is retained from exclusive creation through connection close; a later replacement is not adopted for cleanup. Cleanup cannot turn a completed commit into an error. This receipt does not transport scratch-cleanup warnings; failed cleanup can leave scratch. Non-Unix scratch deletion is conservative, and the recovered held-plan publication route currently fails closed on non-Unix until native file identities are qualified. Windows bridge admission therefore remains an implementation and platform gate. No hard power-loss or hostile same-user post-fence mutation guarantee follows.
